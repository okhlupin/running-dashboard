# Как оформить результат прожарки

Пошаговая инструкция: что и в каком порядке записывать в файлы.

Главный источник правил — `AGENTS.md` проекта. Этот файл описывает только
специфику прожарки: как отличить прожарённую идею от сырой.

---

## 1. Определить номер

Номер = наибольший из:

- максимальный номер истории в `docs/ROADMAP.md`;
- максимальный номер папки в `docs/tasks/`.

Плюс 1. Например: истории до № 20, папки до `task-017` → следующий номер **21**.

**Номера существующих историй не меняются.** Новая история вставляется в свой блок
ROADMAP, но получает следующий свободный номер — так на неё уже можно ссылаться.

Имя папки: `task-NNN-<короткое-имя-на-английском>` — строчными буквами, через дефис.
Например: `task-021-heatmap-metric`.

---

## 2. История в ROADMAP

Формат — как у остальных историй:

```
21. **[Тег]** Я как пользователь дашборда хочу <что сделать>, чтобы <что получить>.
```

- Один тег из списка легенды: `[Удобство]` `[Структура]` `[Ясность]` `[Инфо]` `[Метрики]`.
- История — одна фраза, в стиле существующих: «Я как бегун хочу …, чтобы …».
- Кто пользователь — тот, кто реально будет этим пользоваться. Если это владелец
  данных — «Я как бегун», если любой посетитель — «Я как пользователь дашборда».

**Два дополнительных раздела, если их ещё нет** (создать в конце `docs/ROADMAP.md`):

```
### Отложенные идеи

| Идея | Почему отложили | Когда вернуться |
|---|---|---|

### Отклонённые идеи

| Идея | Почему отклонили |
|---|---|
```

Заполняется при соответствующем вердикте. Смысл — чтобы отклонённое не
предлагалось снова через месяц.

## 3. Папка задачи

Структура — по `AGENTS.md`:

```
docs/tasks/task-NNN-<имя>/
├── TASK.md
├── prompt.md
├── payload.json
└── mockups/
    ├── <имя>-wireframe.md
    └── <имя>-mockup.html
```

### TASK.md

Разделы — как в `task-005-kpi-groups` и `task-017-goal-forecast`:

| Раздел | Что внутри |
|---|---|
| Шапка таблицей | номер, название, раздел ROADMAP, теги, приоритет, статус, зависимости, влияет на |
| User story | фраза по шаблону «Я, как …, хочу …, чтобы …» |
| Контекст | что уже есть в приложении, что с этим делать (со ссылками на строки кода) |
| Цель | 1–2 предложения |
| Пользовательский сценарий | шаги + таблица краевых случаев |
| Требования | P0 / P1 / P2, пронумерованные |
| Формулировки интерфейса | точные надписи, таблицей |
| Макеты и схемы | какие файлы что содержат |
| Тест-вектора | примеры с ожидаемым результатом |
| Критерии приёмки | список галочек |
| Риски и как их снимать | таблица «риск — снятие» |
| Вне рамок задачи | чего делать не надо |
| Связанные материалы | ссылки |

**Правила, которые отличают прожарённую задачу от сырой:**

- В разделе «Контекст» есть таблица «что уже есть и как используем» — со ссылками
  на конкретные строки `running-dashboard 3.html`. Если функцию не нашёл — так и
  написать, а не выдумывать.
- В «Пользовательском сценарии» есть таблица краевых случаев: минимум 4 строки.
- В «Требованиях» P0 — одна мысль, а не пять. Всё, что можно сделать позже, — в P1.
- В «Критериях приёмки» каждый пункт проверяется в браузере. Пункт «работает
  корректно» — плохой. Хороший: «карточка показывает 88.0 / 75 км (117 %) и бейдж
  зелёный».
- В «Рисках» минимум 3 строки.
- В «Вне рамок» перечислены истории ROADMAP, которые эта задача закрывает частично
  или не трогает.

### prompt.md

Готовый промпт для агента, который будет делать задачу. Структура — как в
`task-017-goal-forecast/prompt.md`:

1. Кто ты и над чем работаешь (один самодостаточный HTML-файл, без сборщиков).
2. Что нужно сделать — нумерованный список P0, затем P1.
3. Точные формулы, если есть расчёт.
4. Жёсткие ограничения: что нельзя ломать (экспорт/импорт, демо-данные, фильтры, темы).
5. Обязательные тексты интерфейса — таблицей.
6. Как проверять — пошагово.
7. Чек-лист перед сдачей — галочки.

### payload.json

Валидный JSON. Обязательные части:

```jsonc
{
  "meta": { "taskId": "task-021", "title": "...", "roadmapItem": 21 },
  "defaults": { /* значения по умолчанию */ },
  "storage": { /* какие ключи в state и localStorage */ },
  "examples": [
    {
      "name": "Обычный случай",
      "input": { /* ... */ },
      "expected": { /* ... */ },
      "note": "что именно проверяется"
    }
  ]
}
```

Минимум 4 примера: обычный случай, крайний (пустые данные), противоположный
(значения в другую сторону) и проверка формулы на конкретных числах.

### mockups/

- `<имя>-wireframe.md` — схема экрана в виде текста (ASCII), с подписями блоков,
  и отдельные схемы состояний (обычное, пустое, с ошибкой).
- `<имя>-mockup.html` — кликабельный макет: открывается в браузере, показывает
  разные состояния, работает в тёмной и светлой темах, без ошибок в консоли.

---

## 4. Проверка перед сдачей

- [ ] `payload.json` — валидный JSON (открыть и распарсить, не на глаз).
- [ ] Макет открыт в браузере: переключение состояний работает, ошибок в консоли нет,
  горизонтальной прокрутки нет.
- [ ] В ROADMAP нет дублей: поиск по ключевым словам из новой истории.
- [ ] Новая история не дублирует уже готовые задачи (`docs/tasks/`).
- [ ] Номер новой задачи больше всех существующих и ни с чем не конфликтует.
- [ ] Все ссылки внутри TASK.md ведут на существующие файлы.
- [ ] В `TASK.md` статус — «к выполнению» (задача ещё не сделана).

Запись в `docs/CHANGELOG.md` в этот момент **не** делается — она появится, когда
задача будет выполнена (по правилам `AGENTS.md`).
