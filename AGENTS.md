# Правила работы над проектом

Этот файл — постоянная инструкция для ИИ-агента, который работает над этим проектом.
Прочитай его целиком до начала работы.

---

## 1. Где искать задачи

**Единственный источник задач — файл `docs/ROADMAP.md`.**

Других источников задач нет. Если задачу нужно взять в работу — бери её оттуда.
Не придумывай задачи, которых нет в `docs/ROADMAP.md`, и не работай «по своей инициативе»
за пределами списка, если об этом прямо не попросил пользователь.

---

## 2. Порядок работы над задачей

### Шаг 1. Выбрать задачу

Открой `docs/ROADMAP.md`, найди нужную историю, запомни её номер (например, № 17)
и её точный текст.

### Шаг 2. Проверить, есть ли папка задачи

Папка задачи лежит здесь: `docs/tasks/task-NNN-<короткое-имя>/`
(например, `docs/tasks/task-017-goal-forecast/`).

- **Папка есть и заполнена** — изучи её, особенно `TASK.md`, и продолжай работу по ней.
- **Папки нет** — создай её сам по шаблону (раздел 3 ниже).
- **Папка есть, но файлы пустые** (как `task-001-auth` и `task-002-payment`) — заполни их по шаблону.

### Шаг 3. Сделать задачу

Выполняй задачу в коде приложения. Файл приложения: `running-dashboard 3.html`
(один самодостаточный HTML-файл, всё внутри — разметка, стили и скрипты).

### Шаг 4. Проверить

Проверь, что задача действительно работает: открой результат в браузере и посмотри,
что всё на месте, ничего не сломалось, в консоли нет ошибок.
Не говори «готово», пока не проверил.

### Шаг 5. Перенести задачу в «Готовые»

После выполнения задача переезжает в раздел **«Готовые задачи»** в `docs/CHANGELOG.md`:
добавь туда запись (дата, номер, название, ссылка на папку) и подробный лог ниже по датам.

Подробности формата — в самом `docs/CHANGELOG.md`.

---

## 3. Шаблон описания задачи

Когда папки задачи нет, создай её. Внутри — четыре файла и папка макетов:

```
docs/tasks/task-NNN-<короткое-имя>/
├── TASK.md          — описание задачи
├── prompt.md        — готовый промпт для ИИ-агента
├── payload.json     — пример данных (цифры, настройки, проверочные примеры)
└── mockups/         — схемы и кликабельные макеты
```

### Главное правило шаблона

Описание задачи начинается с фразы **в таком виде**:

> **Я, как пользователь, хочу сделать то-то, то-то, чтобы получить что-то, что-то.**

Здесь:
- **«то-то, то-то»** — что именно человек хочет сделать (действия, которые он совершает);
- **«что-то, что-то»** — что он получит в итоге (результат, польза).

Это та же логика, что и в `docs/ROADMAP.md`, только словами пользователя, а не разработчика.
Пример из реальной задачи (№ 17):

> Я, как бегун, хочу видеть прогноз даты достижения цели по текущему темпу, чтобы понимать, реально ли успею к объёму месяца или квартала.

### Что должно быть в `TASK.md`

| Раздел | Что в нём |
|---|---|
| Шапка таблицей | номер, название, раздел ROADMAP, теги, приоритет, статус, зависимости |
| User story | фраза по шаблону выше |
| Контекст | что уже есть в приложении и что с этим делать |
| Сценарий | что видит человек шаг за шагом |
| Требования | список P0 (обязательно) / P1 (желательно) / P2 (потом) |
| Формулировки интерфейса | точные надписи и подписи |
| Критерии приёмки | список галочек «сделано / не сделано» |
| Риски | что может сломаться и как это предотвратить |
| Границы задачи | чего в этой задаче делать **не** надо |

### Что должно быть в `prompt.md`

Готовая инструкция для ИИ-агента, который будет править код:
что сделать, какие формулы, что нельзя ломать, как проверить, чек-лист перед сдачей.

### Что должно быть в `payload.json`

Пример данных: настройки по умолчанию, структура хранилища, пример пользовательских данных,
проверочные примеры с ожидаемым результатом. Файл должен быть валидным JSON.

### Что должно быть в `mockups/`

- Схема в виде текста (ASCII) — как выглядит экран, где что находится.
- Кликабельный HTML-макет — отдельный файл, который открывается в браузере и позволяет
  посмотреть разные состояния (обычное, пустое, с ошибкой, с данными).

## 4. Язык — главное правило

**Пиши по-русски, простыми словами. Технический жаргон — не нужен.**

Ты пишешь для человека, который не программист. Он открыл дашборд, чтобы посмотреть свои
пробежки, а не чтобы изучать код.

### Как это выглядит на практике

| Не надо | Надо |
|---|---|
| «Имплементировать drag&drop-реордеринг KPI-групп» | «Перетаскивать карточки между группами мышкой» |
| «Прокинуть колбэк в обработчик renderKPIs» | «Пересчитать карточки, когда данные изменились» |
| «Валидировать payload перед записью в localStorage» | «Проверить, что данные нормальные, и только потом сохранить» |
| «Использовать Math.ceil для округления вверх» | «Округлить вверх, до целого числа» |
| «Захардкодить кейс» | «Обработать этот случай отдельно» |
| «Добавить юнит-тесты» | «Проверить расчёт на нескольких примерах и убедиться, что ответ верный» |

### Если термин всё-таки нужен

Иногда слово без знания не обойтись. Тогда:

1. используй его **один раз**, в скобках или сразу после него дай пояснение;
2. пояснение — **простыми словами, без вложенных терминов**;
3. дальше по тексту можешь использовать это слово спокойно.

Примеры:

- **«JSON-файл (обычный текстовый файл, где данные записаны в строках вида "ключ": значение)»**
- **«localStorage (память браузера: данные остаются после перезагрузки страницы)»**
- **«чистая функция (функция, которая только считает и ничего не меняет вокруг себя)»**
- **«callback / обработчик события (код, который срабатывает, когда пользователь что-то нажал)»**
- **«drag&drop (перетаскивание мышкой)»**
- **«юнит-тест (проверка расчёта на заранее известных примерах)»**

### Правило на будущее

Когда пишешь тексты для людей (подписи на странице, названия кнопок, пояснения) —
только простые слова. Без «среднего темпа в км/нед с учётом скользящего окна».
Лучше: «Ваш обычный темп за последние 4 недели».

## 5. Как выглядит готовая задача

Папка задачи остаётся на месте — это документация. Но статус меняется:

1. в `TASK.md` в шапке статус становится **«выполнено»** (дата выполнения);
2. в `docs/CHANGELOG.md` в разделе **«Готовые задачи»** появляется строка со ссылкой;
3. ниже, в логе по датам, появляется подробная запись: что сделано, какие файлы тронуты, как проверялось.

---

## 6. Что нельзя делать

- Не брать задачи не из `docs/ROADMAP.md`.
- Не переписывать уже выполненные задачи в логе — лог только дополняется.
- Не удалять папки выполненных задач.
- Не ломать то, что уже работает: экспорт данных, импорт, демо-данные, фильтры, темы.
- Не отвечать пользователю «сделано», не проверив результат в браузере.
- Не заваливать пользователя техническими деталями в ответе. Отвечай так же просто, как пишешь документы.

## 9. Скилл «Прожарка идеи»

В проекте есть скилл `.opencode/skills/idea-grill/` — он превращает сырую идею
в готовую задачу через разговор с человеком.

**Когда применять:** человек приносит новую идею, хочет разобрать список идей,
отсеять лишнее или проверить готовую задачу на дыры.

**Как применять:** вызвать скилл через инструмент `skill` с id `idea-grill`
(или написать в чат `@idea-grill`).

**Что он делает:**

1. Задаёт вопросы — по одному в главном раунде, пакетами — когда нужно выбрать вариант.
2. Оценивает идею по четырём осям: польза, усилия, риск, уверенность.
3. Сравнивает варианты таблицей и ранжирует их.
4. Проверяет, есть ли нужные данные в приложении, и не дублирует ли идея
   существующую историю.
5. На выходе: история в `docs/ROADMAP.md` + папка `docs/tasks/task-NNN-<имя>/`
   по шаблону из раздела 3.

**Чего он не делает:** не пишет код приложения и не создаёт папку задачи без
подтверждения вердикта. Вердикт бывает трёх видов: делать, отложить, отклонить —
задача получается не всегда.
